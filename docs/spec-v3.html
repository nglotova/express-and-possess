1. Description

Express & Possess is a website where users express their wishes, and the other users of the group take the responsibility to make these wishes come true, free of charge.

The idea came from home. My teenagers keep asking for things to buy and send the links to me and my husband over WhatsApp. In the flow of other messages the links get lost, and the kids send them again. I want one place where everyone in a group such as a family can see the wish lists of the others, plus the list of what they themselves have promised to provide.

The same system can serve a company, where employees request hardware or access codes and a colleague takes care of the request.

The website must work well on a phone. The design is simple and generic, and every page is laid out for a narrow screen first.

2. Roles and statuses

People

  • Member: any registered user who belongs to at least one group.
  • Group admin: the member who created the group. The only person who can edit the group, invite and remove members, close, archive, or delete it. While the group is open, the group admin can also set any status on any wish in it, or delete the wish, with a reason; a hidden implementer stays hidden from them.
  • Creator of an expression: the member who wrote the wish.
  • Implementer: the member who took care of the wish. An expression has at most one implementer at a time.
  • System administrator: a user whose account carries the ADMIN role. Sees the administration page. Ordinary members never see it.

Expression statuses

One name per state, used everywhere: in the lists, on the expression page, in notifications and in the database.

StatusMeaningWho can change it
ExpressedWritten down, nobody has taken care of it yet.Creator can edit or delete. Any other member can take care.
In ProcessAn implementer has claimed it and is working on it.Implementer can update their section, mark it provided, or release it. Creator can still delete it.
ProvidedThe implementer says it is bought or made.Creator ticks Got it. Nobody can delete.
In PossessionThe creator has received it. Closed.Nobody. The page is read-only for everyone.

Group statuses

  • New: no expression has ever been created in the group.
  • Working: at least one expression exists.
  • Closed: the admin closed it. Members still see it, nobody can add or change expressions.
  • Archived: kept in the database, shown nowhere except the administration page.

New and Working are not stored. They are computed from whether the group has any expressions, so they can never get out of step with the data. Closed and Archived are stored.

Decision: Take Care is the claim Clicking Take Care records the implementer and sets In Process in the same instant. The second section that opens afterwards only edits details on an expression the person already owns. If two members click Take Care at the same moment, exactly one succeeds; the other sees "Already taken by someone else" and the page reloads. In v2 the claim could be read as happening on the later Submit, which would let two people fill the section at once.

4. Login and registration

A traditional login page: email, password, Login button. After login the user lands on My Groups.

Below the form, two links:

  • New user? opens the registration form: email (used as the username), password, repeat password, name. The name is first and last name or a nickname. The Register button creates the account and goes to My Groups.
  • Forgot your password? asks for the email and sends a reset link.
Decision: names need not be unique v2 validated the name for uniqueness across the whole system. That rule only existed to make a global user list usable, and the global list is gone (see the group page). The email is the unique identifier; two members named Alex can coexist.

Someone who opens an invitation link (see the group page) without an account is taken to this registration form with the email already filled in, and joins the group as soon as registration completes.

5. My Groups

The landing page after login. It lists the groups the current user belongs to, including the ones they created. A user in no group sees an empty list with the Create group button.

Each row shows:

  • Group name
  • Owner (the group admin)
  • Status: New, Working, or Closed
  • A flashing red ! when the group has expressions that nobody has taken care of yet
  • A warning sign when the current user is the implementer of an expression that is In Process in this group

Tapping a row opens Group activity. The Create group button at the bottom opens Create group.

The header of every page carries the app name, the notification bell with an unread count, and the user's name, which opens the Profile.

6. Profile

Opened from the user's name in the header. Fields:

  • Name, editable
  • Email, shown but disabled
  • Change password link, in the traditional way
  • Notification channels: in-app is always on; email on or off; Telegram, when connected (see Notifications)
  • Save button, returns to My Groups

7. Create and edit a group

Any member can create a group and becomes its admin. Only the admin sees the editing controls; other members see the same page read-only, with a Leave group button.

  • Group name, text field.
  • Status, shown: New by default, then Working, Closed, or Archived.
  • Members: the current members with their role. Each row except the admin's has a Remove control. Pending invitations are listed with "invited, not joined" and a Cancel control.
  • Invite by email: the admin types an address and taps Send. If the address already has an account, that user is added at once and gets an in-app notification. If not, an email with a one-time link goes out; the person joins after registering.
  • Share link: a checkbox "Anyone with the link can join". While ticked, a link is shown that the admin can copy into a family chat. Unticking it invalidates the link. Ticking again makes a new one.
  • Save stores the group and makes it visible to its members.
  • Close sets the status to Closed. Expressions become read-only.
  • Delete group and Archive group appear only when the group is Closed. Delete removes it from the database with everything in it. Archive keeps it but hides it from everyone except the system administrator.
Decision: invitations replace the user picker v2 showed a paginated list of every registered user with checkboxes and asked for other ideas. A global list exposes every user's name to every other user (a real problem once the public demo exists) and stops being usable past a few dozen accounts. Invitation by email is what every comparable product does, and the share link covers the family case where typing four addresses feels like work.

When membership changes

  • A removed member, or one who leaves, stops seeing the group.
  • Their expressions stay in the group, still labelled with their name, so the others can decide what to do with them. The former member can no longer edit them; the admin can delete them.
  • Any expression they were implementing is released, exactly as if they had pressed Release, and its creator is notified.
  • The admin cannot leave. To hand over a group, the admin picks another member as the new admin from the members list (a "Make admin" control), then may leave.

8. Group activity

The top shows the group name and a link to Group users. Below are three sections. Every row in every section is a link to the Expression page.

  • My expressions: the current user's wish list in this group. Columns: picture, description, by date, providing by date, providing by user, status.
  • My implementations: other users' expressions where the current user is the implementer. Columns: picture, creator, description, by date, providing by date, status.
  • Not taken yet: other users' expressions with status Expressed. Columns: picture, creator, description, by date.

The Create expression button sits under My expressions.

Decision: no database identifiers on screen v2 showed the numeric ID as the first column of every list. On a phone the column costs a fifth of the width and tells the reader nothing. The ID stays in the URL of the expression page and in the API; the picture thumbnail takes its place as the row's anchor.

9. Expression

One page with three sections. Who can edit which section depends on their role; everyone in the group can see all three. When the status is In Possession the whole page is read-only.

Section 1: the wish (creator edits, others see)

  • Creator's name, shown.
  • Description, mandatory. Links inside open in a new browser tab. Locked from the moment someone takes care until the expression is released.
  • Picture, optional. When the description contains a product link and no picture was chosen, the system fetches the page's preview image and title and uses them as the picture. The creator can replace it.
  • By date, optional: when the creator would like to have it.
  • Got it checkbox, enabled only when the status is Provided.
  • Submit: saves the section. If Got it is ticked the status becomes In Possession.
  • Delete: removes the expression with its comments. Hidden when the status is Provided or In Possession. If the expression is In Process, the implementer is notified that it was withdrawn.

Section 2: taking care (implementer edits, others see)

While the status is Expressed and the viewer is not the creator, this section is a single Take Care button. Pressing it claims the expression: the implementer is recorded, the status becomes In Process, the creator is notified, and the fields below appear.

  • Implementer's name, shown, or "Incognito".
  • Incognito checkbox, optional. While ticked, the implementer's name is replaced by "Incognito" in every list, on this page, in notifications, and their comments are signed "Anonymous helper". The system administrator can still see who it is.
  • Providing by date, optional.
  • Provided checkbox: the wish is bought or made.
  • Submit: saves the section. If Provided is ticked the status becomes Provided and the creator is notified.
  • Release: the implementer backs out. The section is cleared, the status returns to Expressed, the description unlocks, and the creator is notified. Available only while In Process.
Decision: Incognito hides the name in comments too v2 showed the real name in comments while hiding it elsewhere, which reveals the person the first time they ask a question. Either the option hides the name everywhere or it is not worth having. Comments by an incognito implementer are signed "Anonymous helper".

Section 3: comments (anyone in the group)

  • Earlier comments, oldest first, each with the author's name and time.
  • A text area with a Send button. A sent comment appears at the end and the text area clears.
  • Comments close when the status becomes In Possession.
Decision: comments stay open until In Possession v2 closed them at Provided, but Got it happens after Provided, so the creator could not say thanks. Closing at In Possession keeps the thread open exactly as long as the expression is.

10. Group users and a user's expressions

Group users lists every member of the group: name, email, and a mark if the member has created any expression. Tapping a row opens that user's expressions.

A user's expressions shows the selected member's name and their wish list in this group, with the same columns as My expressions. Each row opens the Expression page. The back link returns to Group users.

11. Administration

A page visible only to accounts with the ADMIN role. It is reached from the header menu, not through a separate login. The role is assigned in the database, or by an existing administrator on this page.

  • Users: list, search, disable an account, grant or revoke the administrator role. Adding users is done through invitations like everyone else.
  • Groups: list including archived ones, open any group read-only, restore an archived group, delete a group.
  • Expressions: set any expression to any status, or delete it, with a mandatory reason. The reason is written to the expression's comments as a system note and sent to the creator and the implementer. Moving a wish on from Expressed when nobody took care of it needs an implementer, chosen from the group's members: for example a gift bought without pressing Take Care. The group admin has the same controls on the expression page, for the wishes in their group.
Decision: an ordinary account with a role, not a special login v2 said "reachable only by Administrator with a special login". A role on a normal account is simpler to build, is what Spring Security does natively, and is the role-based access control worth showing in a portfolio.

12. Notifications

A notification is produced whenever something happens to an expression that concerns a member other than the one who did it:

EventWho is told
New expression createdevery other member of the group
Take Care, Release, Providedthe creator
Got itthe implementer
Expression deleted while In Processthe implementer
New commentthe creator, the implementer and everyone who commented before, except the comment's author
Status set or expression deleted by an administrator or the group adminthe creator, the implementer and the previous implementer, with the reason
Invited to a group, removed from a group, group closedthe member concerned, or all members

Notifications are delivered through channels the member can switch on in their profile:

  1. In-app, always on. The bell in the header shows the unread count; opening it lists the notifications, newest first, each linking to the expression. The flashing ! and the warning sign on My Groups are computed from the same data.
  2. Email, optional. One message per event, with a link.
  3. Telegram, optional, later. The member connects a Telegram bot from the profile page and gets each event as a message. This is the messenger channel: teenagers read Telegram, and its bot API is free.

13. Navigation

v2 worried about forgotten Back buttons. The rule that removes the problem: pages do not have their own Back buttons. The browser's back gesture, backed by the router's history, returns to wherever the user came from. Each page shows one explicit parent link in the header instead, which is always the same regardless of route taken:

  • Group activity, Create/edit group, Group users: parent is My Groups.
  • Expression: parent is the group.
  • A user's expressions: parent is Group users.
  • Profile, Administration: parent is My Groups.

After Save, Submit, Register and Login the app navigates to the page named in that section; after Delete or Leave it goes to the parent.

14. Technology and hosting

The project serves two purposes: a working tool for a family, and a portfolio piece that shows the technologies job postings ask for that my résumé currently lists as basic: Kotlin, Kafka, caching, PostgreSQL, TypeScript, React.

Backend

  • Spring Boot 3, Java 21, one deployable application organised by domain: auth, groups, expressions, comments, notifications, outbox.
  • Notifier as a separate small service in Kotlin, consuming the Kafka topic.
  • PostgreSQL with Flyway migrations.
  • Spring Security with session cookies; password reset by emailed token.
  • Spring Cache with Caffeine for the group list and unread counters.
  • Testcontainers for integration tests, including one that fires twenty concurrent Take Care requests and asserts exactly one wins.

Frontend

  • React with TypeScript, built with Vite.
  • React Router for pages, TanStack Query for data.
  • Installable as a progressive web app so it sits on the phone's home screen.
  • Narrow layout first; the same pages widen on a desktop.

Hosting

  • One Docker Compose file runs postgres, kafka, api, notifier, web, and Mailpit.
  • A small virtual server, one for the family instance and one for the demo.
  • GitHub Actions runs the tests on every push.

Take Care under load

Two members may press Take Care at the same time. The claim is one conditional update, which the database executes atomically:

UPDATE expressions
   SET implementer_id = :me, status = 'IN_PROCESS', version = version + 1
 WHERE id = :id AND implementer_id IS NULL AND status = 'EXPRESSED'

If no row was changed, someone else won and the server answers 409 Conflict. Optimistic locking with a version column covers ordinary edits; no pessimistic lock is needed anywhere.

The public demo

The family instance is private. A second instance at a demo. address is seeded with a fictional family and has three buttons on its login page: log in as Alice, Bob, or Carol. Reviewers can create wishes, take care of them from another browser, and watch the notification arrive. The Mailpit inbox is exposed on the demo so the emails can be seen too. The demo database resets every night. The README links to it, shows the architecture diagram above, and states plainly that Kafka is oversized for a family and why it is there anyway.
